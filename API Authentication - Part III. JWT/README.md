# API Authentication — Part III. JWT — The Self-Contained Token

The third article in the API authentication series opens by naming the hidden cost that both Basic Auth and API Keys share: a database roundtrip on every request. Every time an API key arrives, the server must pause, query a data store for the key's permissions, expiry date, and revocation status, and wait for an answer before doing any real work. For a single service at moderate load this is manageable, but the article shows why it becomes a genuine scalability problem in two specific situations: high request volume (thousands of identity lookups per second) and microservice architectures where a single user action passes through several independent services, each of which independently re-verifies the caller's identity. The database becomes a bottleneck that every service depends on.

JSON Web Tokens solve this by flipping the model. Instead of handing the server an opaque ticket and forcing it to look up the details, a JWT has the details printed on it — and cryptographically stamped in a way that proves the content hasn't been forged. The article uses the boarding-pass analogy to make this tangible: a boarding pass already states your name, flight, seat, and boarding time, right on the paper; the gate agent reads it and checks its authenticity without phoning headquarters. A server holding the right verification key can validate a JWT locally, with no database involved. This property is called statelessness, and it is the core architectural advantage that drove JWT's adoption.

The article also places JWT in its historical context: the server-side session era of the 2000s, the pressure created by single-page applications and mobile clients that made cookies impractical across domains, and the IETF OAuth working group's decision to standardize a compact token format — published as RFC 7519 in May 2015. It introduces the wider JOSE family (JWS for signing, JWE for encryption, JWK for key representation) and is notably honest about JWT's trade-off: information embedded in a token cannot be un-embedded, which creates a genuine difficulty when a token needs to be revoked before its expiry. That tension is the thread that leads into Part IV on OAuth 2.0.
