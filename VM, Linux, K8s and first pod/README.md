# A Computer Inside Your Computer

The first part of a three-part series written for CST8277 Enterprise Application Programming, which builds a complete, reproducible development environment from an empty virtual machine up to a Spring Boot service running on Kubernetes. The series opens with a familiar classroom problem: half the students have a working setup while the other half fight port conflicts, mismatched library versions, and permissions changed by long-forgotten installations. The remedy is to stop installing course software on the host at all and to build a **virtual machine** instead, one that starts empty, receives exactly the tools the course needs, behaves the same on Windows, macOS, and Linux, and can be deleted and rebuilt in under an hour.

The article explains what a VM is, the difference between type 1 and type 2 **hypervisors**, and how to size the guest (4 cores, 8 GB of memory, and 60 GB of dynamically allocated disk, with a practical minimum below that). It also covers why Apple silicon Macs need the ARM64 edition of Ubuntu while everything else needs AMD64. It then walks through creating the VM in VirtualBox, including why to uncheck unattended installation, and installing **Ubuntu 26.04 LTS** page by page, explaining why "Erase disk" is safe inside a VM. After the first boot and system update, an optional section explains **NAT** networking and sets up a port forward so the VM can be reached over SSH from the host's own terminal. The article ends with a troubleshooting guide for slow VMs, freezes, and boot failures caused by the wrong ISO edition.

## Part 2: A Kubernetes Cluster of Your Own

The second part turns the VM into a single-node Kubernetes cluster. It frames Kubernetes as a **control loop**, a thermostat that compares the desired state with the actual state and acts on the difference, while warning that it cannot fix a program that crashes on start. After comparing Minikube, kind, K3s, and **MicroK8s**, it installs MicroK8s 1.36 as a snap, explaining the `--classic` and `--channel` flags and the log-out required for group membership to take effect. A first `kubectl get all` listing introduces namespaces, pods, Deployments, ReplicaSets, DaemonSets, and Services. A throwaway `nginx` workload is then created, exposed through a NodePort, deliberately deleted to watch it self-heal, and scaled to three replicas. The article then enables the built-in **image registry** at `localhost:32000` for the students' own images and installs **Headlamp**, the official successor to the archived Kubernetes Dashboard, with a clear warning about the lab-only `cluster-admin` binding used to log in.

## Part 3: From Source Code to a Running Pod

The final part walks the full chain from source code to JAR, image, registry, pods, and Service, stopping to verify each link. It installs OpenJDK 25, Maven, Docker (with a firm warning against `chmod 666` on the Docker socket), and IntelliJ IDEA. It then generates a Spring Boot 4 project with Spring Initializr and writes a small REST service that uses a Java `record` as its DTO, an `AtomicLong` request counter, and Actuator **liveness and readiness probes**. The service is packaged with a **multi-stage Dockerfile** that leaves the JDK and Maven behind and runs as an unprivileged user, then tested locally and pushed to the cluster registry. Finally, it is deployed declaratively from a YAML manifest with two replicas, probes, resource requests and limits, and a NodePort Service. The counter values returned across replicas make **horizontal scaling** and the problem of in-memory state visible, and deleting the pods demonstrates self-healing and readiness gating once more. The article closes with a tour of Headlamp's overview, workloads, and cluster map, a pod-status decision guide (`ImagePullBackOff`, `CrashLoopBackOff`, and more), and learning activities on rolling updates, rollbacks, and deliberate fault injection.
