# Debugging SSH Connections — A Comprehensive Guide

A systematic troubleshooting reference for SSH connection failures, written for developers and system administrators who already know how to use SSH but find themselves staring at a cryptic error and unsure where to start. The article opens by explaining a deliberate design choice in SSH: error messages are intentionally vague to avoid leaking system information to potential attackers. This means the same terse output can have multiple root causes, and effective debugging requires understanding the protocol's connection sequence rather than pattern-matching on error strings. The article maps out the five stages of an SSH handshake — TCP connection, protocol version exchange, key exchange, client authentication, session establishment — so readers can reason about at which stage a particular failure is occurring.

The main body of the article works through the most common error classes with concrete diagnostic commands and annotated output. "Connection refused" points to a stopped `sshd` daemon, a firewall blocking port 22, or DNS resolution failures — each verified with `systemctl status sshd`, `iptables -L`, and `ping`/`telnet` respectively. "Host key verification failed" is traced to changed server fingerprints (common after OS reinstalls or IP reuse) and resolved by removing the stale entry from `~/.ssh/known_hosts`. "Permission denied (publickey)" is diagnosed through a checklist of file permission requirements — `~/.ssh` must be `700`, `authorized_keys` must be `600` — and verified using `ssh -vvv` verbose output. Cloud-specific scenarios are also addressed: AWS security groups, GCP firewall rules, and the difference between instance-level and VPC-level network ACLs.

The article rounds out with guidance on using SSH's built-in verbose modes (`-v`, `-vv`, `-vvv`) as a first-line diagnostic tool, and on reading server-side logs (`/var/log/auth.log` on Debian/Ubuntu, `journalctl -u sshd` on systemd systems) when the client-side output doesn't reveal enough. The overall approach is methodical — eliminate network issues first, then authentication issues, then configuration issues — and works just as well for a local homelab as for a production cloud environment.
