# API Authentication — Part I. Basic Authentication

This is the opening article in a multi-part series on API authentication. Before getting into any specific mechanism, it takes time to establish a conceptual foundation by clearly separating two concepts that developers often conflate: authentication (proving identity — "who are you?") and authorization (granting access — "what are you allowed to do?"). The airport analogy used throughout — a passport for authentication, a boarding pass for authorization — sets the tone for the series and makes the distinction memorable. The article then surveys the history of API authentication, tracing how simple username-and-password mechanisms evolved as systems shifted from single-server web apps toward distributed, service-oriented architectures.

With that context in place, the article dives into Basic Authentication — the oldest and simplest HTTP auth mechanism still in widespread use. It explains how credentials are combined into a `username:password` string, base64-encoded, and attached to every request via the `Authorization: Basic …` header. Both sides of the exchange are demonstrated in Python: a client function that constructs the header, and a server function that reverses the encoding and validates the credentials. The article is deliberately honest about what base64 is and is not — an encoding scheme, not encryption — making clear that HTTPS is non-negotiable when using Basic Auth in production.

The article closes by weighing Basic Authentication's trade-offs. Its strengths are simplicity and near-universal support; its weaknesses are that credentials travel with every request, there is no built-in token expiry, and managing per-user passwords at scale becomes cumbersome. These limitations motivate the rest of the series: API Keys in Part II, JWTs in Part III, and OAuth 2.0 in Part IV. Suitable for developers who are new to API security or want a solid conceptual baseline before tackling more sophisticated mechanisms.
