# Building Pace Maker or how I did load testing

An article about building Pace Maker, a small native macOS load testing app written in Swift and SwiftUI, born out of frustration with how much ceremony heavyweight tools such as JMeter demand for the quick, everyday question of whether an endpoint will survive a few hundred requests per second. The app is designed for a backend developer who already knows the endpoint and needs a fast, trustworthy feedback loop, so the live chart owns the window while settings live in a hideable inspector.

The central architectural idea is **separating pacing from concurrency**. Requests are released on a schedule derived from the target rate alone, pass through a bounded backlog to a fixed worker pool, and are admitted by an **adaptive connection gate** that sizes in-flight concurrency roughly by Little's law and backs off when errors climb while throughput stalls. Excess requests are shed and counted instead of buffered, which keeps the **backpressure honest**: the achieved rate visibly drops below the target exactly when the server can no longer keep up. The article then turns to **measuring honestly**, describing subtle bugs such as per-window failures compared against per-second successes, and the fixes: every series normalized to requests per second, an error rate based on finished requests, and the final partial window excluded from the chart.

Further sections cover composing real requests across all common HTTP methods, with a body editor that disables macOS smart quotes so JSON isn't silently corrupted, and a layered architecture (SwiftUI views → observable session model → engine facade → transport adapters) that keeps redraws cheap and the pure logic unit-testable. The roadmap includes gRPC, WebSocket, and raw TCP adapters, and signed builds are available in the [public repository](https://github.com/eugenezimin/Pace-Maker).
