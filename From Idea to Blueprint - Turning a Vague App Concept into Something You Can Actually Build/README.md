# From Idea to Blueprint — Turning a Vague App Concept into Something You Can Actually Build

The first lesson in the "Build a Twitter Clone" series, which takes a deliberately different starting point: instead of opening a code editor, it opens a blank page. The central argument is that "build a Twitter clone" is a wish, not a plan. A single-sentence idea hides hundreds of unmade decisions — can users edit posts after publishing? what happens on an empty submit? who is responsible for storing a message once it's sent? — and code is the most expensive place to discover that a decision was skipped. The article uses the blueprint analogy to make this concrete: moving a wall on paper costs a pencil eraser; discovering the same mistake after the concrete is poured costs a demolition crew. The same economics apply to software, and diagrams are the cheapest medium in which to be wrong.

The article then introduces the three-lens modelling framework that the entire series is built on. The first lens is **behaviour**: a flowchart that captures what the app should do, step by step, including decision points and failure paths — the answer to "what should it do?" The second lens is **structure**: a functional (block) diagram that identifies what system components must exist to deliver that behaviour — the answer to "what parts must exist?" The third lens is **interaction**: a sequence diagram that shows how those components communicate at runtime — the answer to "how do those parts talk to each other?" The order is deliberate: structure is derived from behaviour, and interaction is derived from structure, so nothing is invented from thin air. A scoped messaging app called `Bird` serves as the running example throughout the series, small enough to model completely but realistic enough to encounter genuine design questions.

The lesson closes by reframing what a diagram is. It is not documentation produced after the work is done. It is the instrument used to turn the wish into the plan — a shared picture that a whole team can argue over, annotate, and agree on before a single line of code is written. For developers who habitually skip straight to implementation and pay for it later in rework, this lesson offers both the justification for slowing down and the specific tools for doing so productively.

## Lesson 2: The Blueprint Beneath the Blueprint — Designing `Bird`'s Data Model and Choosing Its Database

The second lesson in the series defers the promised diagrams by one lesson, arguing that a diagram drawn without a data model is a sketch rather than a specification. The central claim: before any flowchart can be drawn for "Post a message," the system must know exactly what a message *is* — which fields it carries, where it lives, and how it connects to its author. The lesson walks through all three use cases and reads them for data clues, arriving at two distinct entities (`User` and `Message`) and five tables across two purposefully separated databases.

The database split is the lesson's main architectural decision. Instead of one monolithic database, the system uses `ums` for identity and access (users, roles, sessions) and `twitter` for content and social graph (messages, subscriptions). The reasoning is grounded in the **Database per Service** pattern and **Domain-Driven Design** bounded contexts: the word "user" in the identity domain and "author" in the messaging domain model the same human being differently, and coupling those models in a single database is convenient now and costly later. Every field in the resulting MySQL schema is traced back to a specific use case, with UUIDs chosen over auto-incrementing integers for distribution safety, and the `subscriptions` table included preemptively because adding it later would require a schema migration.

## Lesson 3: Drawing the Blueprint — Flowchart, Functional Diagram, and Sequence Diagram

The third lesson makes good on the promise deferred since Lesson 1: with the data model in place, all three diagrams are drawn. Working through "Post a message" as the single traced example, the lesson constructs the flowchart, functional diagram, and sequence diagram in strict order, demonstrating that each is derived from the one before rather than invented from scratch.

The flowchart is built by naming start and end points, walking the happy path, and adding three decision gates — authentication check, permission check, content validation — with their branches and a shared error node. The functional diagram is read directly off the flowchart by asking, for each step, which component must own that responsibility; the result is four components (Frontend Client, Twitter Service, UMS Service, MySQL) with no invented API Gateway or standalone auth service. The sequence diagram assembles those components into lifelines and traces the exact message sequence, including the non-blocking `WebClient` call to UMS and the `INSERT INTO messages` that follows a passed role check. The lesson closes by putting all three diagrams side by side to demonstrate **traceability**: the permission check that appears as a decision diamond in the flowchart, an arrow in the functional diagram, and an `alt` block in the sequence diagram is the same decision at three levels of resolution — each level revealing something the others cannot.
